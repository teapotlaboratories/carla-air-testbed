The one remaining socket call is chase_jpeg — the third-person view, the only thing the console needs that the ROS surface does not publish. Whether it gets a topic is step 4, and the plan says to decide it with the console in hand rather than in advance.

1 Three lanes out, and only one is the product

The page talks to its own server over /api/…. That is private plumbing between a browser tab and the process serving it — no user of this project touches it, and it is not an interface the simulator offers. What matters is what the server does next, and that is now almost entirely ROS 2: the same topics and services your own agent would use.

The 6.6% is not zero, and the baseline is not "console closed"

Subscribing removed the second AirSim capture, but re-encoding to JPEG still costs the machine that is also rendering. And the baseline in that comparison is the console running and idle, not absent — an idle ROS console still converts every frame, so its idle cost sits inside the baseline while an idle socket console costs nothing. The comparison is biased toward ROS; 6.6% is a floor on the total, not the total. A true no-console baseline is unmeasured.

3 Two things it refuses to do

Both return 409, not 500. Nothing has failed — the console has declined, and says what to do instead. The shape is deliberate and shared: decline and explain, rather than either acting or greying a button out with no reason.

RefusalWhy
Flying while another node publishes setpoints Two publishers on /fmu/in/trajectory_setpoint produce no error at all — just an aircraft that goes somewhere neither asked for. examples/ros2_full_control.py measured a takeoff to NED 35 m arriving at 15.6 m. Includes reset, which is a /sim/* service but flies the aircraft — a hole found in review, because “flight command” and “moves the aircraft” are different sets
Stopping the stack it is running inside With --in-stack the console's container joins the simulator's namespaces, so docker rm -f kills this server mid-request and the browser sees a dropped connection rather than an error. Destructive and silent about it

4 Both deployments work now

The previous version of this page ended with a red broken arrow: the console could not reach the containerised stack by any route. That is closed. It runs on the host against either deployment, or inside the stack with ./scripts/webui.sh --in-stack.

Two detection assumptions that were wrong, and only the live run found them

/run/.containerenv cannot tell you that you are inside the stack — it is present for this whole project on this machine, so inferring it would refuse the stop button for every ordinary console. And the ROS image ships no docker binary, so a console inside the stack asking docker ps concluded there was no stack and took the host path. Every unit test passed throughout, because they injected that answer rather than computing it.

5 The one open decision

chase_jpeg is the last socket call, and the chase camera is the only thing the console needs that the ROS surface does not publish. Three answers, and the cheap ones are not obviously wrong:

OptionCostConsequence
Build a chase video topic real work An image_transport pipeline whose only consumer is this page, adding a continuous second capture to the path just optimised
Leave it on the socket free The honest claim becomes “flying is ROS; the chase view and lifecycle are not” — two documented exceptions rather than one
Drop the pane free Chase recording already works as a service for episodes; the live view is a convenience

A fourth exists and resolves the tension rather than trading it away: a topic that publishes only while something is subscribed, so it costs nothing when nobody is watching. More work than either cheap option, and genuinely optional.
