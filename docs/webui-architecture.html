The web console, and the gap to the containers

webui/server.py is the only way to look at this simulator by hand rather than through a scripted episode. It works — against the host bringup. The containerised stack that landed on 2026-08-06 does not know it exists, and this page is what that costs, where the break is, and what it would take to close it.

Two of those zeros are the whole story. Zero ROS calls is R-03, filed 2026-08-03 and re-planned 2026-08-07: every flight button bypasses the interface this project claims is the interface. Zero appearances in the stack is newer and undocumented — no image builds it, no script starts it, and docs/containers.html does not mention it once.

1 What it is

A stdlib ThreadingHTTPServer on the 3.10 side, serving one HTML page, two MJPEG streams and a small JSON API. It runs from ./.venv/bin/python webui/server.py and reuses the sidecar RPC surface that run_episode.py already uses, rather than opening a second path to the simulator.

It holds three separate Unix-socket connections, not one shared (webui/server.py:204-207). That is deliberate: sharing one would interleave a control write with a 40 kB frame read, which is a failure this repository has already paid for once.

Why the process path shells out

Processes (webui/server.py:126-201) deliberately runs the project’s own scripts instead of reimplementing them. Those carry the Vulkan ICD repair, the GPU 1 pin, the VRAM check that catches software rendering, and the path-scoped process matching that keeps drone-sim alive. A second implementation would drift from them silently — and the stop button is exactly where a stray pkill -f would take out a sibling project’s flight gate.

The console contends with the ROS graph

The onboard view is a real AirSim capture and that image path is the bottleneck. Streaming it at 10–12 Hz while an episode runs roughly halves the rate the model sees. The console is for manual flying with the graph down, and the page says so rather than silently degrading a scored run.

3 Where it meets the container stack

It doesn’t. The console was written on 2026-08-02, four days before the stack existed, and nothing in docker/ or scripts/stack_*.sh mentions it. The two lanes below both work; there is simply no edge between them.

What does know about it

Process management, and only process management. scripts/status.sh:49 counts the console, and scripts/stop.sh:30 includes webui/server.py in its name list — so ./scripts/stop.sh --all takes it down correctly. It is the container layer specifically that has never heard of it.

4 R-03: the control path is not ROS 2

Separate from the container gap, and older. Every flight button — velocity, yaw, hold, land, takeoff — goes over the Unix socket to the sidecar, and the method name arrives from the browser, validated only against the allowlist: 

# webui/server.py:328-332
method = body.get("method")
if method not in protocol.METHODS:
    raise RuntimeError(f"unknown method {method!r}")
self._json({"result": CONTROL.call(method, **body.get("args", {}))})

All 30 sidecar methods are reachable that way, including spawn_traffic, set_weather, destroy_actors and shutdown — not just the flying ones. The console therefore proves nothing about whether the ROS 2 surface is sufficient, which was the entire point of building it that way.

One honest carve-out, already recorded in R-03

Start the simulator and stop everything cannot become ROS calls. There is no graph to call into before the simulator exists, and the stop button’s whole job is to destroy the graph. Those stay process management. Flying the aircraft is the part that must be ROS.

5 Reaching it from off the machine

The console binds 127.0.0.1 by default. --bind netbird resolves the wt0 mesh address from ip rather than guessing it, and going off loopback generates a token by default rather than on request — an unauthenticated endpoint that starts processes and flies an aircraft is reachable by every peer on the mesh. The check is hmac.compare_digest, and the URL is also written to out/webui-url.txt at mode 0600 so a backgrounded server’s token survives a lost log.

This is not the same path as the ROS graph

Remote ROS 2 access goes through scripts/discovery_server.sh and configs/dds/udp-only.xml — measured at 17.9 Hz over NetBird and 16.1 Hz over the LAN. The console is a second, unrelated remote surface with its own auth. Closing R-03 would collapse them into one; today they are two.
