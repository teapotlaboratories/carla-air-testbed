The sidecar RPC path

Where it lives, how a call flows, and where one slow reply takes the whole graph down. Every number here is measured on this machine; every path is a real file and line.

The finding, in one sentence

The request/reply stream has no correlation between a reply and the call that asked for it — so when a caller gives up at 60 s, the reply it abandoned is still delivered, and every later call on that connection reads the previous call's answer. Forever.

1  Where it lives

Two processes, because they must be: the CARLA-Air client is an ABI-tagged cpython-310 extension and ROS 2 Jazzy is 3.12, so neither interpreter can load the other's C extensions. They are joined by a Unix domain socket carrying msgpack frames — a 4-byte big-endian length, then the object.

Four connections, not one. Image capture takes ~500 ms and telemetry ~5 ms; sharing one socket collapsed /fmu/out/vehicle_odometry from 20 Hz to 1.5 Hz. Each connection is served by its own thread with its own AirSim client.

2  How a call flows

A healthy call is dull, which is the point. The caller holds a per-connection lock, writes one frame, and blocks reading the next one.

The id is on the wire and nobody reads it. call() assumes the next frame off the socket is its own reply. That assumption is the entire defect.

3  Where it breaks

reset is the only call that routinely exceeds 60 s. It is not a teleport: AirSim destroys and rebuilds the vehicle, and the aircraft is then placed and given a holding setpoint. Measured on this box — 26.8 s flying back from the goal, 5.5 s once placed directly, and considerably worse under load.

When it exceeds the ceiling, the socket read raises — and nothing else happens. The request is still in flight. The sidecar finishes and writes its reply into a socket nobody is reading.

The stream is now permanently off by one. Every later call gets the previous call's answer. There is no resync, no id check, no reconnect — so this never recovers on its own.
Why this looked like four unrelated bugs

Every downstream symptom traces back to that single off-by-one: KeyError: 'position' killing bridge_node; Broken pipe and Connection reset by peer immediately after; all four world services failing together (they share self.world); and the sidecar dying of an uncaught carla::client::TimeoutException — a poisoned connection is exactly what leaves CARLA's own RPC unanswered long enough to hit its ceiling and call terminate().

5  The fix: correlate, don't wait

The wire format already carries an id in both directions. Nothing uses it. Give each connection a reader thread and a map from id to a waiting slot, and a late reply becomes harmless rather than poisonous.

Timeouts stop being a correctness mechanism. They become a statement of caller patience: getting one wrong costs a failed call, not a dead graph.
And the proactive half

Progress frames give the thing a fixed timeout never can: the difference between slow and dead. A reset that is genuinely working can take three minutes without anyone panicking; a reset that has wedged fails in seconds, because the progress stops arriving.
