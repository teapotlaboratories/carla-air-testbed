The stack in containers

Three containers, one GPU, and a drone you fly over ROS 2 from outside all of them. This page is what runs where, how a frame gets from the render thread to your code, and the two ways to reach the graph — both measured on 2026-08-06, neither guessed.

What runs where

The split is not a packaging preference. libcarla is an ABI-tagged cpython-310 extension and ROS 2 Jazzy is 3.12; neither interpreter can load the other’s C extensions. That is why this project is two processes, and why it is two images.

ContainerImageInterpreterWhat it does
carla-air-simcarla-air/sim:v0.1.7— CarlaUE4 on the GPU. Owns the network and IPC namespaces and serves CARLA on :2000 and AirSim on :41451.
carla-air-bridgecarla-air/sim-bridge:13.10 The sidecar. Holds the carla and airsim clients and answers RPC over a Unix socket.
carla-air-roscarla-air/ros:13.12 The bridge node. Turns sidecar RPC into /fmu/*, /camera/*, /sensors/* and the /sim/* services.

Flying it from outside the containers

The simulator ships no navigator. Whatever decides where the aircraft goes is yours, and it connects over the public ROS 2 interface like any other client. There are two ways in, and the choice is about which namespace your code lives in.

Read this before debugging a silent graph

The containers share one IPC namespace and Fast-DDS prefers shared memory over loopback UDP. A process on the host is in a different IPC namespace, so it discovers the graph and then receives nothing. Measured: ros2 topic hz on the host reported NO DATA for topics publishing at 16 Hz inside. Nothing errors. This is not a bug to fix — it is what containerising a DDS graph means.

Route A — run your node in the stack

Faster, and what stack_run.sh exists for. Your container joins the same network and IPC namespaces, so shared memory works.

# bring the stack up
./scripts/stack_up.sh --config configs/testbed.yaml

# anything in the repo, inside the stack
./scripts/stack_run.sh -d examples/navigation/run.sh
./scripts/stack_run.sh scripts/run_episode.sh --scenario cross_the_plaza --seeds 1

# or your own image, joined by hand
docker run --rm -it \
  --network container:carla-air-sim \
  --ipc container:carla-air-sim \
  -e ROS_DOMAIN_ID=42 \
  your/agent:latest

Route B — stay on the host

Slower and simpler. Force Fast-DDS off shared memory and the graph appears.

# measured: /fmu/out/vehicle_odometry at 13.9 Hz from the host
export FASTRTPS_DEFAULT_PROFILES_FILE=$PWD/configs/dds/udp-only.xml
export ROS_DOMAIN_ID=42
ros2 topic hz /fmu/out/vehicle_odometry

Nothing here ships an agent

examples/ros2_full_control.py takes off, flies a waypoint, holds a velocity, commands an attitude and lands — importing nothing from this project. That is the test that the interface stands on its own, and it is why the answer to “how do I control the drone” is the same whether you are in a container or not.

Three things that had to be right

Each was found by it failing, and each fails in a way that names something else.

WhatSymptom if you skip it
--ipc shareable on the simulator the ROS container will not start: failed to join IPC namespace … non-shareable IPC. --ipc host is refused by this daemon under rootless/nested Docker.
repository mounted at its own absolute path Package 'bringup' not found. colcon build --symlink-install fills the install tree with absolute symlinks; any other mount point leaves them dangling.
python3-msgpack in the ROS image the bridge node dies at import with a bare ModuleNotFoundError naming nothing about the seam — protocol.py imports it at module scope.
And the one that cost five days

GPU passthrough was recorded as impossible here. It was a missing GLVND package set: libGLX_nvidia.so.0 is a GLVND vendor library, and without libglvnd0/libgl1/libegl1 it loads and exposes no entry points — then falls back to llvmpipe silently. Plus a symlink, because the injected ICD names a Fedora path that does not exist in an Ubuntu container. Full account in docs/worklog/2026-08-06-gpu-in-a-container.md.

Proving it is on the GPU

A container that started is not a container that is rendering, and the software fallback is silent. run_sim_docker.sh refuses to report success without the VRAM check; these are how you confirm it yourself. 

# the process, and what it holds — expect GB-scale against a container path
nvidia-smi --query-compute-apps=pid,process_name,used_memory --format=csv,noheader
#   383488, /opt/carla-air/CarlaUE4/Binaries/Linux/CarlaUE4-Linux-Shipping, 3318 MiB

# sustained load on the card you asked for, and only that card
nvidia-smi --query-gpu=index,utilization.gpu,memory.used --format=csv,noheader
#   0, 0 %, 115 MiB      1, 42 %, 3434 MiB

# rule out the fallback explicitly — expect 0
docker logs carla-air-sim 2>&1 | grep -caiE 'llvmpipe|lavapipe|swiftshader'

# and always, when the test is done
./scripts/stack_up.sh --down
Teardown is not tidiness

--down removes every carla-air-* container, not just the three it starts, and prints what it left. A leftover container holds 3.3 GB of VRAM exactly like a leftover process does, and the examples and one-shot runs hold the same resources.

Measured 2026-08-06 on the carbonite workstation — driver 610.43.03, Docker 29.6.2 rootless and nested, GPU 1 an RTX 5060 Ti.
