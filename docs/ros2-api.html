Commanding and reading the aircraft over ROS 2

Five commands, twelve sensor streams, all PX4 messages on PX4 topics. Every row in the tables below was executed against the running simulator and the result measured — the "verified" column is what actually happened, not what the code intends.

What you can send

/fmu/in/vehicle_command px4_msgs/msg/VehicleCommand Take off — command = 22, param7 = altitude NED 40 → 40.4
/fmu/in/vehicle_command px4_msgs/msg/VehicleCommand Land — command = 21 0.4 m AGL
/fmu/in/trajectory_setpoint px4_msgs/msg/TrajectorySetpoint Position target — position set, velocity NaN +45.0 → +45.5 m
/fmu/in/trajectory_setpoint px4_msgs/msg/TrajectorySetpoint Velocity target — velocity set, position NaN 5 m/s x 5 s → 27.9 m
/fmu/in/vehicle_attitude_setpoint px4_msgs/msg/VehicleAttitudeSetpoint Roll / pitch / yaw — quaternion in q_d +/-15 deg exact, all axes
Both target types share one topic, and velocity wins

The bridge checks velocity first, so a message with both fields finite is a velocity command and the position is ignored. Unused fields must be NaN, not 0.0 — zeros are a command to hold still, so a position setpoint sent with a zeroed velocity field is silently a "stop".

Two things that make everything silently fail

ROS_DOMAIN_ID=42. On the default domain this graph merges with a sibling project publishing real PX4 topics of the same name. You will see topics and read another aircraft's data.

QoS must be best-effort and transient-local. A RELIABLE subscription receives nothing from these publishers, with no error and no warning — the topic simply looks connected and never delivers. 

from rclpy.qos import (QoSDurabilityPolicy, QoSHistoryPolicy,
                       QoSProfile, QoSReliabilityPolicy)

PX4_QOS = QoSProfile(
    reliability=QoSReliabilityPolicy.BEST_EFFORT,
    durability=QoSDurabilityPolicy.TRANSIENT_LOCAL,
    history=QoSHistoryPolicy.KEEP_LAST,
    depth=5,
)

Sending commands

Take off and land

from px4_msgs.msg import VehicleCommand

pub = node.create_publisher(VehicleCommand, "/fmu/in/vehicle_command", PX4_QOS)

msg = VehicleCommand()
msg.timestamp = int(node.get_clock().now().nanoseconds / 1000)
msg.command   = VehicleCommand.VEHICLE_CMD_NAV_TAKEOFF   # 22
msg.param7    = 40.0                                  # altitude, metres NED
msg.target_system = 1
msg.from_external = True
pub.publish(msg)

# land: same message, command = VehicleCommand.VEHICLE_CMD_NAV_LAND  (21)

Position target

import math
from px4_msgs.msg import TrajectorySetpoint

pub = node.create_publisher(TrajectorySetpoint, "/fmu/in/trajectory_setpoint", PX4_QOS)

msg = TrajectorySetpoint()
msg.timestamp    = int(node.get_clock().now().nanoseconds / 1000)
msg.position     = [150.0, -159.4, -40.0]   # north, east, DOWN (NED)
msg.velocity     = [math.nan] * 3            # NaN, not 0.0 - see the trap above
msg.acceleration = [math.nan] * 3
msg.jerk         = [math.nan] * 3
msg.yaw          = math.nan                # or radians to face a heading
msg.yawspeed     = math.nan
pub.publish(msg)                           # fire once; it flies there and holds

Roll / pitch / yaw

from px4_msgs.msg import VehicleAttitudeSetpoint

def euler_to_quaternion(roll, pitch, yaw):     # radians, FRD
    cr, sr = math.cos(roll/2),  math.sin(roll/2)
    cp, sp = math.cos(pitch/2), math.sin(pitch/2)
    cy, sy = math.cos(yaw/2),   math.sin(yaw/2)
    return [cr*cp*cy + sr*sp*sy, sr*cp*cy - cr*sp*sy,
            cr*sp*cy + sr*cp*sy, cr*cp*sy - sr*sp*cy]

pub = node.create_publisher(
    VehicleAttitudeSetpoint, "/fmu/in/vehicle_attitude_setpoint", PX4_QOS)

msg = VehicleAttitudeSetpoint()
msg.timestamp        = int(node.get_clock().now().nanoseconds / 1000)
msg.q_d              = euler_to_quaternion(0.0, math.radians(15.0), 0.0)
msg.yaw_sp_move_rate = 0.0
msg.thrust_body      = [0.0, 0.0, -0.5]
pub.publish(msg)   # STREAM this at ~10 Hz
Velocity and attitude must be streamed; position and takeoff must not

A velocity or attitude command has a lifetime (0.5 s by default) and the aircraft stops when it lapses. Send one and it is obeyed for half a second. That is deliberate: a client that dies mid-command leaves an aircraft that coasts to a halt rather than one that keeps flying.

Position, takeoff and land are one-shot — they run to completion on their own.

Take the aircraft off the autonomy loop first

bringup.sh starts the VLM → grounding → control chain, and that controller streams its own setpoints at 10 Hz onto /fmu/in/trajectory_setpoint. Two publishers on one topic is not a conflict either can detect: the bridge forwards whichever arrived last, and at 10 Hz the autonomy loop wins. Measured symptom — a takeoff commanded to NED 40 m reached 15.6 m and the aircraft flew where the VLM wanted, with no error anywhere. 

# from a shell
ros2 param set /offboard_control enabled false

Reading sensors

from px4_msgs.msg import SensorCombined, SensorGps, VehicleAirData, \
                          VehicleMagnetometer, VehicleOdometry
from sensor_msgs.msg import PointCloud2

node.create_subscription(VehicleOdometry, "/fmu/out/vehicle_odometry", on_odom, PX4_QOS)
node.create_subscription(SensorCombined,  "/fmu/out/sensor_combined",  on_imu,  PX4_QOS)
node.create_subscription(VehicleAirData,  "/fmu/out/vehicle_air_data", on_baro, PX4_QOS)
node.create_subscription(VehicleMagnetometer, "/fmu/out/vehicle_magnetometer", on_mag, PX4_QOS)
node.create_subscription(SensorGps,       "/fmu/out/sensor_gps",       on_gps,  PX4_QOS)

# The lidar comes from CARLA, not from the flight-controller shim,
# so it uses an ordinary QoS depth rather than PX4_QOS.
node.create_subscription(PointCloud2, "/sensors/lidar/points", on_lidar, 1)

def on_odom(msg):
    north, east, down = msg.position          # metres, NED
    w, x, y, z        = msg.q                 # orientation quaternion

def on_lidar(msg):
    # 24 bytes per point: 4f (x, y, z, cos_inc_angle) + 2I (object_idx, object_tag)
    import struct
    for i in range(msg.width):
        x, y, z, cos_inc, obj_idx, obj_tag = struct.unpack_from(
            "<ffffII", msg.data, i * msg.point_step)
Two frame facts that cause real bugs

NED altitude is not height above ground. On Town10HD the origin sits 27.45 m above the street, so -position[2] = 40 means 67.45 m AGL. Confusing these has already broken a scenario in this project.

LiDAR points are in CARLA's frame relative to the sensor — x forward, y right, z up — while everything else in the graph is NED with z down.

How these numbers were obtained

Every command was published from a ROS node, from a known reset state, and the effect measured from /fmu/out/vehicle_odometry. Nothing here is copied from a message definition and hoped for.

Testing found a bug that reading the code would not have

The first attitude run returned pitch +15 commanded, -15.0 achieved, and yaw likewise inverted while roll was correct. Symmetric and exact on both signs, so a convention mismatch rather than drift: AirSim's moveByRollPitchYawZAsync does not use the same handedness for pitch and yaw that its own orientation reporting does. It is corrected at that one call, so everything above it — PX4 messages, the ROS graph, this page — speaks one consistent NED/FRD convention.

A complete working client is in examples/ros2_full_control.py. It imports nothing from this project — only rclpy, px4_msgs and sensor_msgs — which is the test that the ROS surface is genuinely self-sufficient.
