# 2026-08-04 — auditing every doc the README points at

Prompted by the operator noticing the README looked out of date. Checked all seven linked
docs. Every link resolved; the content was another matter.

## The one that mattered: `docs/ros2-api.html` published wrong intrinsics as measured

The README bills that page as *"every figure measured against the running simulator"*. It
stated:

    /camera/rgb/image_raw    640x480, bgr8, step 1920
    /camera/rgb/camera_info  fx 320.5, fy 320.5, cx 320.0, cy 240.0

The shipped config has been `960x720` for some time. Read off the running graph:

    width 960  height 720  encoding bgr8  step 2880
    k = [480.808, 0, 480.0,  0, 480.808, 360.0,  0, 0, 1]

Anyone writing a pixel→ray transform from that page got it wrong by 1.5x — and this project's
entire grounding path is a pixel→ray transform. A doc that says "measured" and is wrong is
worse than one that says nothing, because it is trusted without checking.

**Worth noting how nearly I got this wrong too.** I first *computed* fx as `(960/2)/tan(45°) =
480.0` and was about to write that. The measured value is **480.808**, because the real
horizontal FOV is 89.9°, not 90 — the figure `bringup.sh` prints on every start. Rule 6 caught
it: the arithmetic was defensible and still not the number the graph publishes. Anything
labelled measured now comes from `ros2 topic echo`, not from a calculator.

The same page documented **zero** `/sim/*` services — one passing use of the word "service" and
no mention of `ResetVehicle`, `SpawnTraffic`, `DestroyActors`, `SetWeather`, `SetCameraPose` or
`ChaseRecording`. The branch's headline change, world control on ROS 2, never reached the ROS 2
API reference. Added as a table, verified against `ros2 service list` on a running graph, with
a note that `/sim/collision` and `/sim/traffic_stats` are topics rather than services.

## Rates, re-measured rather than adjusted

Everything quoting rates was quoting a 640x480 measurement. Measured 2026-08-04 with the full
graph up and no VLM attached:

| topic | was documented | measured |
|---|---|---|
| `/fmu/out/vehicle_odometry` | 20.0 Hz | 19.5 Hz |
| `/camera/rgb/image_raw` | 7.8 Hz (640x480) | **8.1 Hz (960x720)** |
| `/camera/depth/image_raw` | 7.8 Hz | 7.9 Hz |
| `/fmu/in/trajectory_setpoint` | 10.0 Hz | 10.000 Hz |

**The camera rate did not fall.** 2.25x the pixels at the same ~8 Hz, which says the bottleneck
is the readback and transport rather than the render — consistent with what
`docs/architecture.md` already claims about the float readback, and the first direct evidence
for it. Had the rate table simply been edited to match the new resolution, that would have been
missed entirely.
