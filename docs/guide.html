VLM navigation testbed · ROS 2 Jazzy · CARLA-Air v0.1.7

A drone that flies where a model points

Reproduces the See-Point-Fly loop — frame → 2D annotation → 3D displacement → velocity setpoint — against a photorealistic city with live traffic and weather. Headless, on one GPU, with no containers.

The autonomy nodes talk to /fmu/out/* and /fmu/in/* exactly as they would to a real Pixhawk 6C, so they port to hardware by deleting one node rather than rewriting the stack.

The loop

sim_bridgepy3.10 · carla + airsim
bridge/fmu/out/* · /camera/*
vlm_client/vlm/annotation
grounding/vlm/grounded_waypoint
control/fmu/in/trajectory_setpoint

the ground world — CARLA traffic, pedestrians, weather  ·  the aircraft — ROS 2 Jazzy, PX4-shaped topics

Two processes because it has to be: the CARLA-Air client is an ABI-tagged cpython-310 extension and ROS 2 Jazzy is 3.12, so neither interpreter can load the other's C extensions.

Project rule

Every flight test ends with stop.sh --all. The simulator holds 3.3 GB of VRAM while idle, and a leftover graph stacks on the next bringup — two controllers then fight over the aircraft while ros2 node list still looks correct.

What this does not say

Every failure here is max_steps — nothing crashes, and there were zero collisions across all 50 episodes. geometric wanders.

The oracle's 0/5 on avoid_the_block is the intended result, not a regression. The oracle is handed the goal and steers straight at it, so a scenario built to block the straight line defeats it by construction: all five seeds park against the same tower face, 70.0–71.0 m from the goal. A way around exists at 1.18x the direct distance — survey_buildings.py --route proves it — so this is the first scenario where a real model has room to beat both baselines rather than tie them.

The other three scenarios are still solved by a straight line, so a 5/5 there shows the harness reaches goals, not that the scenario is hard. They are left unchanged on purpose: editing them would invalidate the baseline the first VLM backend is meant to be measured against.

Adding a VLM backend

Implement one method — image and instruction in, pixel out — and register it in BACKENDS. The model never sees a pose, a map or metres; all the geometry happens downstream in grounding, which is what keeps backends swappable and the comparison fair.

BackendWhat it does
mockSeeded random pixels. The floor.
scriptedA fixed pixel sequence — a changed outcome is unambiguously a change in the stack, not the model.
geometricSteers toward the most open depth column. The baseline a real VLM must beat to be worth its latency.
oracleA diagnostic, not a competitor. Handed the goal, so it answers whether a scenario is navigable at all. Never reported beside a real model's score. It only validates open scenarios: being a straight-line policy, it fails an obstacle scenario by construction, so use survey_buildings.py --route to prove those are reachable.
claudeThe first real model in the loop, over the Anthropic API. Sees the same frame and instruction as the baselines, which is what makes its score comparable. Schema-constrained reply, so the pixel arrives as an integer; effort: low by default because 40 steps in 300 s leaves 7.5 s per decision. Needs ANTHROPIC_API_KEY in the environment — never a ROS parameter. Its SDK is a python 3.12 dependency in vendor/py312, not the 3.10 venv.

Running outside a container

Developed inside a distrobox on a Fedora host, but native Ubuntu 24.04 is the simpler target — exactly one workaround exists because of the container, and it disappears without it.

  • Vulkan ICD (container-only). distrobox injects the host's ICD JSON, so on a Fedora host it names /usr/lib64/libGLX_nvidia.so.0 — absent in an Ubuntu container. On native Ubuntu the driver package ships a correct one. run_sim.sh uses the system ICD when it resolves and synthesises a corrected one only when it does not, so it works either way with no configuration.
  • Everything else is portable. The Python 3.10 venv is needed because Ubuntu 24.04 ships 3.12, not because of the container. ROS_DOMAIN_ID=42 avoids a sibling project's ROS graph. The pkill -f guardrails are universal shell behaviour.

What it is and is not good for

Good for

Developing and benchmarking a VLM navigation client against a photoreal city with dense traffic, weather and segmentation ground truth. Episodes are repeatable to 0.04 m of trajectory divergence, on one workstation GPU, with no build step.

Not for sim-to-real

CARLA-Air contains no PX4 — zero occurrences of px4, mavlink, uxrce or /fmu/ upstream. These /fmu/* topics are a shim over AirSim SimpleFlight: you get portability of your nodes, not a flight controller. Failsafes, lockstep, EKF2 and arming logic need a different lane.

Sweeps run in real time

Both clocks hold RTF 1.000 and faster-than-real-time is unavailable — AirSim's ClockSpeed accelerates the aircraft while CARLA's world stays at 1×, so the two halves desync. Budget timeout × seeds of wall clock.

From nothing to a scored autonomous flight

Quick start

About 40 minutes, most of it the 6.85 GB download and the 18 GB unpack. The three failures you are most likely to hit are all silent — they are in Troubleshooting.

Check the machine first

# all three must succeed
nvidia-smi                                   # driver alive
source /opt/ros/jazzy/setup.bash && ros2 --help >/dev/null && echo "ros2 ok"
ls /usr/share/vulkan/icd.d/nvidia_icd*.json  # a Vulkan ICD exists

  1. Install — one command

    git clone <this repo> carla-air_testing && cd carla-air_testing
./scripts/install.sh                       # ~10 min

# put the 18 GB release somewhere with room - it is remembered
./scripts/install.sh /mnt/big-disk
# or skip the 6.85 GB download entirely
./scripts/install.sh --skip-release

    Four steps, printed as it goes: the CPython 3.10 venv (~2 min), the simulator (~5 min), the pinned upstreams (~40 s) and the colcon build of 7 packages (~3 min). Every step is idempotent, so a failure is resumable — fix it, re-run, and completed steps are skipped.

    There is no export to copy into a shell profile: a non-default release location is written to .release-path and every script resolves it through scripts/release_path.sh. Then verify without touching the simulator: 

    ./.venv/bin/python -m pytest tests/ -q     # expect: 117 passed

  2. Bring the stack up

    ./scripts/bringup.sh --backend oracle

    Wait for these three lines — about 90 s, mostly Unreal loading the map:

    GPU 1 (NVIDIA GeForce RTX 5060 Ti): 3342 MiB in use — hardware rendering confirmed
sim_bridge up on /tmp/carla_air_testbed.sock
[bridge_node-1] bridged to CARLA-Air — map=Town10HD hfov=89.9deg
    3342 MiB matters

    If it reports a few hundred MiB you are rendering on the CPU, not the GPU — RGB capture drops from 53.8 Hz to 5.95 Hz and nothing errors. See Troubleshooting.

    The index is whichever card simulator.gpu asked for — 1 in the shipped config, because GPU 0 is the workstation's display card. On a single-GPU machine set simulator.gpu: 0 before the first run.

  3. Fly a scored episode

    cd carla-air_testing
./.venv/bin/python scripts/run_episode.py --scenario cross_the_plaza --seeds 1
    === cross_the_plaza seed=1 ===
  traffic: {'vehicles': 15, 'walkers': 9}
  start pose: [113.0, -167.1, -55.7] (commanded [107.6, -159.4, -55.0], error 9.4 m)
  episode running [cross_the_plaza-s1-331669] — 'fly across the open plaza…'
    alt  54.4 m  pos [122.1, -173.7, -54.4]
    alt  54.6 m  pos [145.8, -168.5, -54.6]
    alt  54.9 m  pos [169.6, -163.3, -54.9]

    The result lands in out/episodes/<episode_id>.json. A ~9 m start-pose error is normal — the aircraft relaxes about 4 m after reaching a setpoint, which is why success radii are 20 m.

  4. Stop — every time

    ./scripts/stop.sh --all

    This is a project rule, not tidiness — see the note in the readme.

Change something

Everything is configured in one file, configs/testbed.yaml. Its sections are named for when a change takes effect — the difference that actually costs you time.

SectionWhat lives thereCost to change
simulatormap, GPU, camera buffers, GPS origin, clock speed restart the simulator, ~60 s
sensorsevery sensor on the aircraft, both simulators restart the sidecar, ~5 s
sidecarthe chase camera restart the sidecar, ~5 s
graphrates, backend, controller limits, recording live — ros2 param set
configs/testbed.yaml — the complete file 
# The testbed, in one file.
#
# `scripts/apply_config.py` renders this into the formats each reader actually demands:
#
#   configs/sim/settings.json                 AirSim's schema, read by the CarlaUE4 binary
#   ros2_ws/src/bringup/config/testbed.yaml   ROS's schema, read by rclpy's parameter system
#
# Both are GENERATED. Edit this file, not those.
#
# ---------------------------------------------------------------------------------------
# The three sections are named for WHEN a change takes effect, not for which file it lands
# in, because that is the difference that costs you time:
#
#   simulator:   restart the simulator          ~60 s
#   sidecar:     restart the sidecar            ~5 s   (simulator keeps running)
#   graph:       nothing — `ros2 param set`     live
#
# ---------------------------------------------------------------------------------------

simulator:
  map: Town10HD
  gpu: 1                    # nvidia-smi index, or a "10de:2d04" vendor:device pair.
                            # GPU 0 is the operator's and is regularly busy with UnrealEditor.

  # 1.0 and leave it there. AirSim's ClockSpeed accelerates SimpleFlight but NOT CARLA, so
  # anything else desynchronises the two halves of the world.
  clock_speed: 1.0

  # Geodetic origin. Null means AirSim's own default, which is Redmond, Washington and has no
  # relationship to Town10HD — a fine GPS *sensor*, a meaningless *position*. Set all three to
  # pin somewhere deliberate.
  gps_origin:
    lat: null
    lon: null
    alt: 0.0

  # The drone's own cameras. ALL THREE MUST STAY 4:3. `fov` is horizontal, so two buffers with
  # matching fov and different aspect ratios cover different VERTICAL fields, and
  # `frames.scale_to()` then maps an RGB pixel onto the wrong depth pixel — silently, on every
  # waypoint. This is also why the drone camera is not 1920x1080.
  cameras:
    rgb:          {width: 640, height: 480, fov: 90}
    depth:        {width: 160, height: 120, fov: 90}
    segmentation: {width: 320, height: 240, fov: 90}


# ---------------------------------------------------------------------------------------
# SENSORS — one list, whichever simulator provides them.
#
# `source` decides how a sensor is obtained, and the difference is not cosmetic:
#
#   airsim   POLLED over RPC, on the same path as image capture. Costs image rate:
#            5 Hz is -1.7%, 20 Hz is -28%. Measured, not estimated.
#   carla    PUSHED asynchronously from inside UE4. Free-floating actors that follow the
#            aircraft by transform, because CARLA has no actor for an AirSim vehicle.
#            No measurable cost to the image path.
#
# The four AirSim sensors below are created AUTOMATICALLY by AirSim for a multirotor — they
# answer whether or not they appear here. `enabled` controls whether the bridge PUBLISHES
# them, not whether they exist. AirSim LiDAR and distance sensors are the opposite: they do
# not exist without an explicit block and a simulator restart, which is why the lidar here is
# a CARLA one instead.
# ---------------------------------------------------------------------------------------

sensors:
  - name: imu
    source: airsim
    enabled: true
    topic: /fmu/out/sensor_combined          # px4_msgs/msg/SensorCombined

  - name: barometer
    source: airsim
    enabled: true
    topic: /fmu/out/vehicle_air_data         # px4_msgs/msg/VehicleAirData

  - name: magnetometer
    source: airsim
    enabled: true
    topic: /fmu/out/vehicle_magnetometer     # px4_msgs/msg/VehicleMagnetometer

  - name: gps
    source: airsim
    enabled: true
    topic: /fmu/out/sensor_gps               # px4_msgs/msg/SensorGps

  # A point cloud where every point carries the object id and semantic tag of what it hit.
  # Strictly more than depth for obstacle work.
  #
  # RANGE IS THE BINDING CONSTRAINT, not points_per_second — which counts rays CAST, not
  # points returned. With lower_fov -50 and a level sensor the steepest ray is 50 degrees
  # below horizontal, so the ground is only reachable below about `range * sin(50)` = 61 m
  # AGL. Above that this sees buildings and nothing else.
  - name: lidar
    source: carla
    enabled: true
    blueprint: sensor.lidar.ray_cast_semantic
    topic: /sensors/lidar/points             # sensor_msgs/msg/PointCloud2
    offset: {x: 0.0, y: 0.0, z: -0.4}        # metres, body FRD. Negative z is ABOVE.
    attributes:
      channels: "16"
      range: "80.0"
      # 120000 destabilised the simulator: CARLA's own RPC began timing out at 30 s and took
      # the sidecar down with it. Ray casting is CPU work inside UE4 competing with the
      # simulation it samples.
      points_per_second: "30000"
      rotation_frequency: "10"
      upper_fov: "10.0"
      lower_fov: "-50.0"
      horizontal_fov: "360.0"

  # Everything below is off. Kept as working examples — rediscovering the right attribute
  # names costs more than these lines do.

  - name: radar
    source: carla
    enabled: false
    blueprint: sensor.other.radar
    offset: {x: 0.3, y: 0.0, z: 0.0}
    attributes: {horizontal_fov: "45.0", vertical_fov: "30.0", range: "100.0",
                 points_per_second: "3000"}

  # Event camera: per-pixel brightness CHANGES rather than frames. Nothing in the AirSim set
  # is equivalent, and it is a genuinely different signal for a navigation policy.
  - name: events
    source: carla
    enabled: false
    blueprint: sensor.camera.dvs
    offset: {x: 0.5, y: 0.0, z: 0.1}
    attributes: {image_size_x: "640", image_size_y: "480", fov: "90.0"}

  # Object identity, not just class — what would let a scenario say "the second building on
  # the left" and be able to score it.
  - name: instances
    source: carla
    enabled: false
    blueprint: sensor.camera.instance_segmentation
    offset: {x: 0.5, y: 0.0, z: 0.1}
    attributes: {image_size_x: "640", image_size_y: "480", fov: "90.0", sensor_tick: "0.1"}


sidecar:
  socket: /tmp/carla_air_testbed.sock

  # The exterior camera that follows the aircraft. A CARLA sensor, so it is nearly free — but
  # not entirely: measured against the SIMULATOR's tick rate, 30 Hz at 1080p costs nothing
  # (59.8 vs 60.0) while 60 Hz costs 10 fps of simulation. Real-time factor stays 1.000
  # throughout, which is the trap — judge this by tick rate, never by RTF.
  chase_camera:

graph:

Adding a sensor

All of them are one list, whichever simulator provides them. Flip enabled and restart the sidecar. 

sensors:
  - name: lidar
    source: carla                  # pushed from inside UE4 - costs the image path nothing
    enabled: true
    blueprint: sensor.lidar.ray_cast_semantic
    topic: /sensors/lidar/points
    offset: {x: 0.0, y: 0.0, z: -0.4}   # metres, body FRD; negative z is ABOVE
    attributes: {channels: "16", range: "80.0", points_per_second: "30000"}

  - name: radar
    source: carla
    enabled: false                 # <- flip this
    blueprint: sensor.other.radar
source is not cosmetic

airsim sensors are polled over RPC, on the same path as image capture, and that costs measurable frame rate: 5 Hz costs 1.7%, 20 Hz costs 28%. carla sensors are pushed asynchronously from inside the simulator and cost nothing measurable. The file carries the numbers.

radar, events (an event camera) and instances (instance segmentation) are already written out and disabled, so enabling one is a one-word edit.

Two files you must not edit

configs/sim/settings.json and ros2_ws/src/bringup/config/testbed.yaml are generated. AirSim's schema is read by the simulator binary and the parameter file by rclpy, and neither will accept a unified file. Both carry a DO-NOT-EDIT header, both are re-rendered on every start, and a test fails if they drift from their source.

What you just ran

oracle is not a VLM. It is handed the goal and flies straight at it, so it answers one question: is this scenario navigable at all? On the three open scenarios it is the ceiling at 5/5 each, and the geometric baseline scores 0/5. It scores 0/5 on avoid_the_block, which is that scenario working as intended — there is a tower on the straight line, and a straight-line policy cannot get past it. Try the contrast: 

./scripts/stop.sh
./scripts/bringup.sh --backend geometric
# then in terminal 2, the same episode command

Troubleshooting

SymptomCause and fix
Everything is slow; run_sim.sh reports a few hundred MiB of VRAM You are on the lavapipe software rasteriser, not the GPU — 53.8 Hz drops to 5.95 Hz and nothing errors. run_sim.sh regenerates a corrected Vulkan ICD automatically; if it persists, check ldconfig -p | grep libGLX_nvidia finds a library that exists. Common inside a distrobox.
Simulator exits immediately, out/sim.log empty, no crash dump That is what a broken Vulkan ICD looks like. Same fix. It is not a corrupt install.
bringup.sh cannot reach sim_bridge The sidecar could not connect to the simulator. Check out/sim_bridge.log, and that ports 2000 and 41451 are listening: ss -tln | grep -E '2000|41451'.
Topic rates look doubled; two controllers seem to fight A previous graph is still running. ./scripts/stop.sh, then bring up again — status.sh shows a count above 1.
ros2 topic list shows nothing Set the domain — everything here runs on ROS_DOMAIN_ID=42 to stay clear of other ROS graphs on the machine.
A code change has no effect colcon --symlink-install still needs a rebuild for ament_python packages; the symlink is made at build time. Re-run scripts/build_ros.sh.
A config change has no effect Three possibilities, in order of likelihood. You edited a generated file (configs/sim/settings.json or ros2_ws/src/bringup/config/testbed.yaml) instead of configs/testbed.yaml, and the next start overwrote it. Or the setting lives in simulator: and needs the simulator restarted, not just the graph. Or an environment variable is winning: TESTBED_GPU, TESTBED_ORIGIN_LAT/LON/ALT and the bringup.sh flags all override the file, deliberately, so a one-off run needs no edit. scripts/apply_config.py --check answers the first.
import carla fails Use ./.venv/bin/python. The client module is cpython-310; system Python on Ubuntu 24.04 is 3.12 and physically cannot load it.
