Deferred on 2026-08-03 as tidiness with nothing depending on it. Re-planned 2026-08-07, because the containers arrived and turned the current design from untidy into a dead end — and because the job turns out to be a quarter of the size the backlog entry implied.

The two blockers are the ones ranked real work in the architecture report: the socket-path mismatch and the permission-denied volume. An rclpy node needs no socket, so both stop existing rather than getting fixed.

1 Why the answer changed

Nothing about the console changed. Three things around it did.

What changedConsequence
The containers landed 2026-08-06 The console is in no image and reaches the containerised sidecar by no route at all. Porting to rclpy is now the cheapest way to a containerised console — cheaper than joining namespaces with the 3.10 process, because the socket stops being needed
The contention got a name The console opens a second AirSim capture, which is why it carries a do-not-run-during-a-scored-episode warning. On a ROS topic, one capture serves the agent and the console both — a scored run becomes watchable live
The surface was measured, not guessed The console uses 14 of the 30 allowlisted methods, and 13 already exist on ROS 2. This is not “grow the surface to match the console”; it is “make the console use what works”

Measured 2026-08-07 — and it corrected this page

This box used to predict the camera rate would be unchanged with the console open, on the reasoning that one capture fanned out by DDS costs nothing. That was wrong. Three drift-controlled A/B pairs each way, watching /camera/rgb/image_raw while a browser streams:

console closed   6.39–6.66 Hz
socket stream    5.060 Hz   −24.0%
ROS stream       5.968 Hz   −6.6%

Re-encoding to JPEG is not free. The honest claim is 3.6× cheaper, not free — still the difference between a console you must close before a scored run and one you can leave open. A first attempt measured a 10% drop that was inside the baseline's own drift; alternating the conditions is what made the number mean anything.

Row five is proved, not assumed

examples/ros2_full_control.py already flies takeoff, land, velocity and yaw over rclpy + px4_msgs while importing nothing from the testbed. That restriction is what makes it a proof: if a demo of the command surface needed the 3.10 side, the surface would not be closed.

3 Four steps, each shippable alone

4 Two rules the port must not break

Do not invent friendly services to make the port easy

examples/ros2_full_control.py:17-20 refuses a /testbed/takeoff on purpose: moving to hardware must mean deleting carla_air_bridge and starting uxrce_dds_client, not rewriting every client. If porting a button tempts you to add one, the shim is what broke — send a TrajectorySetpoint like any Pixhawk client instead.

The carve-out is permanent, and the honest claim changes

Start and stop can never be ROS calls: there is no graph before the simulator exists, and the stop button’s job is to destroy the graph. Afterwards the true statement is “flying is ROS; lifecycle is not” — not “the only interface is ROS 2”, which will never hold for this component. Better written down now than discovered during the port.

5 What it costs, honestly

Cost or riskSizeNote
JPEG encoding moves into the ROS container small New CPU in the container that also runs the graph. Minor at 12 fps, but not free and worth measuring rather than assuming
The HTTP port must be published from the container small Plus the existing token story carries over unchanged
Chase pane needs an image_transport pipeline deferred Nobody else consumes it. This is exactly why it is step 4 and not step 1
Two remote surfaces become one benefit Today the console and the DDS graph are separate remote paths with separate auth
Nothing depends on the console still true The reason it was deferred has not gone away. What changed is the cost of waiting, not the cost of stopping

6 How it will be verified

Four checks, and the last one is the one that matters — the others only prove the code moved. 

# 1. the socket is gone from the control and video paths
grep -c 'socket' webui/server.py      # → 0 for those paths

# 2. it still works from off the machine
#    every control exercised over NetBird, as the current console already is

# 3. onboard video arrives from a topic, not a capture
ros2 topic hz /camera/rgb/image_raw

# 4. THE ONE THAT MATTERS - the contention is actually gone
#    a scored episode, console open vs closed, comparing the rate the agent sees.
#    unchanged = one capture fanned out. dropped = still two.

Measure the thing the fix was meant to fix

This project has already had a rate guard added to fix one bug that caused another, and an odometry rate that was two simulators added together. Check 4 is not optional paperwork — it is the only one that distinguishes “the console now speaks ROS” from “the console now speaks ROS and still opens a second capture”.
